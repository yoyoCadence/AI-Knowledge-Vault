# Architecture Decision Records

Format for each record: Context → Options → Decision → Reasoning → Trade-offs → Reversal strategy.
Status values: `accepted`, `superseded by ADR-x`, `proposed`.

A note on verification: the build environment for the initial implementation could reach
only the npm registry; vendor documentation sites were blocked. Package APIs were therefore
checked against the docs and type definitions shipped _inside the installed packages_. For
example, Next.js 16 bundles its docs in `node_modules/next/dist/docs/`, and Better Auth
exposes `init-options.d.mts`. Versions were chosen from npm release metadata (dates and
peer dependencies). Anything not verified that way is marked _assumption_.

---

## ADR-001 Modular monolith on Next.js 16 (App Router), Node.js 22, pnpm

- **Status:** accepted
- **Context:** The app has one owner and small scale, but many functional modules (import,
  extraction, search, sharing, backup, later AI). The spec forbids premature microservices.
- **Options:**
  1. Next.js full-stack, plus a separate worker from the same codebase.
  2. A separate API (Fastify) plus an SPA.
  3. Remix or another framework.
- **Decision:** Option 1. Next.js 16.4 App Router, React 19.3, Node.js 22 LTS and
  pnpm 10. Business logic lives in `src/modules/*`, and infrastructure in
  `src/infrastructure/*`. Route handlers and pages are thin adapters.
- **Reasoning:** One language, one deployable image, Server Components for data-heavy reading
  pages, and route handlers for the REST contract. The worker imports the same modules, so
  there is no duplicated domain logic.
- **Trade-offs:** Next.js major versions move fast; `proxy.ts` replaced `middleware.ts` in
  v16. Coupling to Next.js is limited to `src/app/**` and `src/proxy.ts`.
- **Reversal:** Modules have no Next.js imports (enforced by lint rule
  `no-restricted-imports` in `src/modules/**`). Moving to another HTTP framework means
  rewriting only `src/app/**`.

## ADR-002 TypeScript 6.0 (strict), not 7.0

- **Status:** accepted
- **Context:** TypeScript 7.0 (the native Go port) is the latest release, but
  `typescript-eslint` 8.x declares `typescript >=4.8.4 <6.1.0`.
- **Decision:** TypeScript 6.0.x with `strict`, `noUncheckedIndexedAccess`, and
  `exactOptionalPropertyTypes` off (it is too noisy with Drizzle and Zod types).
- **Reversal:** Upgrade to 7.x once `typescript-eslint` supports it. No code changes are
  expected.

## ADR-003 PostgreSQL via node-postgres + Drizzle ORM, versioned SQL migrations

- **Status:** accepted
- **Context:** The spec mandates Neon PostgreSQL and recommends Drizzle, with versioned
  migrations and no destructive `push`.
- **Options:**
  - Drivers: `pg` (TCP), `@neondatabase/serverless` (HTTP/WebSocket), `postgres.js`.
  - Migrations: `drizzle-kit generate` + `migrate`, or `push`.
- **Decision:**
  - Drizzle ORM 0.45 with the `pg` driver.
  - Migrations are generated by `drizzle-kit generate` into `drizzle/` and applied by our
    own runner, `scripts/db-migrate.ts`, which uses `drizzle-orm/node-postgres/migrator`.
  - Hand-written SQL, such as triggers, goes in custom migrations
    (`drizzle-kit generate --custom`).
  - `drizzle-kit push` is not used outside throwaway local databases, and
    `package.json` has no script for it.
- **Reasoning:**
  - `pg` works against Neon (pooled endpoint), local Postgres, CI service containers and
    any future host, so there is no vendor lock.
  - The worker is long-lived, so TCP pooling is ideal.
- **Trade-offs:** On serverless web hosting, use Neon's pooled (PgBouncer) connection string;
  this is documented in `DEPLOYMENT.md`.
- **Reversal:** Swap the driver in `src/infrastructure/database/client.ts` only.

## ADR-004 Authentication: Better Auth, isolated behind `modules/auth`

- **Status:** accepted
- **Context:** The spec calls for email and password, secure sessions, no public sign-up,
  rate limiting, and a future path to Passkey, MFA and OAuth without forcing a third-party
  identity provider.
- **Options:** Better Auth, Auth.js, Lucia-style hand-rolled sessions.
- **Decision:** Better Auth 1.7 with the Drizzle adapter, configured as follows:
  - `emailAndPassword.disableSignUp = true`
  - sessions stored in Postgres
  - `rateLimit.storage = "database"` with stricter custom rules on `/sign-in/*`
  - `telemetry.enabled = false`
  - UUIDv7 IDs via `advanced.database.generateId`
  - tables mapped to our names: `users`, `sessions`, `auth_accounts`,
    `auth_verifications`, `auth_rate_limits`
  - The first admin is created with a CLI (`pnpm admin:create`) that runs only with
    server credentials, never over HTTP.
- **Reasoning:** Self-hosted (data stays in our database), with first-party plugins for
  passkey, two-factor and OAuth later. Hashing is scrypt by default.
- **Trade-offs:** Its schema is opinionated. Mapping table names keeps our naming.
- **Reversal:** All callers use `getActor()`/`requireActor()` from `modules/auth`. Replacing
  Better Auth means re-implementing those functions plus the login and logout endpoints.

## ADR-005 Background jobs: PostgreSQL job table + separate Node worker with leases

- **Status:** accepted
- **Decision:**
  - Table `processing_jobs`; jobs are claimed with `FOR UPDATE SKIP LOCKED`.
  - Leases: `locked_until` is extended by a heartbeat. Expired leases are recovered to
    `queued`, or to `failed` once attempts are exhausted.
  - Exponential backoff via `run_after`.
  - `idempotency_key` is UNIQUE.
  - Concurrency is bounded per worker (`WORKER_CONCURRENCY`).
  - Handlers must be idempotent; each one documents why in its file header.
- **Reasoning:** No extra infrastructure, transactional enqueue (a job is created in the
  same transaction as the business row), and durable across crashes.
- **Trade-offs:**
  - Polling latency (default 1 s, with exponential idle backoff up to 5 s).
  - Throughput is limited to roughly hundreds of jobs per second, far above need.
- **Reversal:** `modules/jobs/queue.ts` is the only module touching the table. A Cloudflare
  Queues or SQS implementation can replace enqueue and claim while keeping
  `processing_jobs` as the status ledger.

## ADR-006 Object storage behind a `StorageAdapter`; content-addressed immutable originals

- **Status:** accepted
- **Decision:**
  - Interface: `putObject`, `getObject` (stream), `headObject`, `deleteObject`,
    `listObjects`, `createSignedUploadUrl`, `createSignedDownloadUrl`.
  - Implementations: `S3StorageAdapter`, which uses the AWS SDK v3 against R2 or any S3
    API, and `LocalStorageAdapter`, a filesystem adapter whose signed URLs are HMAC tokens
    served by `/api/storage/local/*`.
  - Originals are stored at `ws/{workspaceId}/originals/{sha256}` and written with
    `If-None-Match: *` semantics (S3 conditional write; `wx` open flag locally).
  - Staging lives under `ws/{workspaceId}/staging/{importItemId}`. Derived files live under
    `ws/{workspaceId}/derived/{versionId}/…`.
- **Reasoning:**
  - Content addressing makes worker retries idempotent: re-copying the same bytes to the
    same key is a no-op.
  - Conditional writes make an accidental overwrite impossible rather than merely unlikely.
- **Guard:** Local storage is refused in production unless
  `ALLOW_LOCAL_STORAGE_IN_PRODUCTION=true` is set explicitly, for a VPS with a persistent
  volume. That way the app never silently stores files on ephemeral disk.
- **Reversal:** Adapters are swappable by configuration. The migration tool copies objects
  key by key, and keys are provider-neutral.

## ADR-007 Untrusted preview isolation: separate origin + path tokens + CSP + sandbox, no scripts

- **Status:** accepted
- **Decision:**
  - Preview content is served only on `PREVIEW_ORIGIN` at `/p/{token}/{path}`. The token is
    an HMAC-SHA256 over `{versionId, workspaceId, scope, exp}`, with a 15-minute TTL for
    owners and share-scoped for share links.
  - Responses carry this CSP:
    - `default-src 'none'`; `script-src 'none'`
    - `style-src {preview} 'unsafe-inline'`; `img-src {preview} data:`; `font-src {preview} data:`
    - `form-action 'none'`; `base-uri 'none'`; `frame-ancestors {app origin}`
    - `sandbox allow-same-origin` (scripts still blocked)
  - Responses also set `X-Content-Type-Options: nosniff` and
    `Cross-Origin-Resource-Policy: cross-origin`. Files are looked up in the database
    manifest (`derived_assets`), never on a filesystem path.
  - The embedding `<iframe>` uses `sandbox` with no flags, plus `referrerpolicy=no-referrer`.
- **Reasoning:** Defense in depth. Each layer (origin, sandbox, CSP, no cookies, manifest
  lookup) fails independently.
- **Trade-offs:**
  - Interactive artifacts lose interactivity.
  - External fonts and CDNs are blocked, so system fonts are used; this is shown to the user.
- **Reversal:** A future opt-in "interactive preview" uses a dedicated preview runtime with a
  pinned vendored script allow-list (ROADMAP P3-PREVIEW-RUNTIME). It is never enabled by
  relaxing the defaults.

## ADR-008 Identifiers: UUIDv7 generated in the application

- **Status:** accepted
- **Reasoning:** Time-ordered for index locality, globally unique (so restore usually keeps
  IDs), and independent of the Postgres version (`uuidv7()` arrives only in PG 18).
- **Decision:** `uuid` package `v7()`. Better Auth uses the same generator.
- **Amendment (P1A import):** rows created by the import worker are deterministic UUIDv5 values
  derived from the import item ID: the artifact version, the new artifact, and the derived
  assets. This makes retries idempotent, because a re-run targets the same IDs and storage keys.
  These IDs are not time-ordered, which is acceptable for these tables.

## ADR-009 Search: application-level CJK bigram tokenization into `tsvector`, chunk-level index

- **Status:** accepted. See ARCHITECTURE_REVIEW F-06.
- **Options considered:**
  1. Stock FTS: fails on CJK.
  2. `pg_trgm`: weak for two-character queries and dependent on locale ctype.
  3. `zhparser` or `pg_jieba`: not available on Neon.
  4. An external engine (Meilisearch, Typesense): a new service.
  5. Application tokenization (CJK bigrams + Latin words) stored as `tsvector`.
- **Decision:** Option 5, with a GIN index on `content_chunks.search_vector` and
  `artifact_search_documents.search_vector`.
- **Trade-offs:**
  - Bigram indexing over-matches across word boundaries; this is acceptable for personal
    recall, and ranking mitigates it.
  - No Simplified↔Traditional folding yet (OpenCC; ROADMAP P2-SEARCH-OPENCC).
- **Reversal:** The tokenizer is versioned (`search_tokenizer_version`), so a re-index job
  rebuilds vectors. An external engine could consume the same chunks.

## ADR-010 Extraction toolchain

- **Status:** accepted
- **Decision:**
  - HTML: `rehype-parse` → custom hast sanitization (remove script, style, template,
    noscript and hidden nodes; strip `{{…}}` bindings) → `hast-util-to-mdast` →
    `mdast-util-to-markdown` (GFM).
  - Markdown: `mdast-util-from-markdown` (GFM) for sections.
  - PDF: `unpdf`, which wraps pdf.js.
  - ZIP: `yauzl` streaming with our own limits. Writing exports uses `yazl`.
  - Images: `sharp`, with `limitInputPixels`.
  - Text encoding: strict UTF-8, then Big5 and UTF-16 fallbacks via `TextDecoder`.
- **Reasoning:** Pure JavaScript (except sharp), streaming-capable, maintained, and no
  browser required.
- **Versioning:** Every extractor has `extraction_method` + `extraction_version`.
  Re-extraction creates a new `extracted_documents` row and never touches originals.

## ADR-011 Share links store only a token hash

- **Status:** accepted. See ARCHITECTURE_REVIEW F-09.
- **Decision:**
  - The token is 32 random bytes encoded base64url (256 bits).
  - The database stores `sha256(token)`; lookups are by hash.
  - Links are shown once.
  - Each link has independent flags: `allow_preview`, `allow_reading`, `allow_download`
    (default false), plus `expires_at` and `revoked_at`.
  - Links only resolve while `artifact.visibility ∈ {unlisted, public}`.

## ADR-012 Portable export format v1

- **Status:** accepted. The full specification is in `BACKUP_RECOVERY.md`.
- **Decision:** A ZIP containing:
  - `manifest.json`, `schema-version.json`, `README.txt`
  - `metadata/*.json`
  - `originals/{sha256[0:2]}/{sha256}/{sanitized filename}`
  - `normalized/{versionId}.md`
  - `checksums.sha256`, in GNU `sha256sum` format, so `sha256sum -c` verifies it without
    this app.

  Optional outer encryption uses `age`.

## ADR-013 Testing stack

- **Status:** accepted
- **Decision:**
  - Vitest 4.1 for unit tests and for integration tests against a real PostgreSQL. CI uses
    a `postgres:16` service; locally, any Postgres works. Tests never mock the database.
  - Playwright 1.56.1 for E2E, pinned to match the Chromium build pre-installed in the
    development container (`chromium-1194`). Upgrade when the container image changes.
- **Reasoning:** Integration tests prove SQL, constraints and triggers. Mocked databases
  would hide exactly the bugs this system must not have.

## ADR-014 Deployment topology

- **Status:** accepted for design; not yet deployed.
- **Decision:**
  - A single Docker image (Next.js `output: "standalone"` plus a bundled worker) runs as
    two processes: `web` and `worker`.
  - Primary data: Neon PostgreSQL and Cloudflare R2.
  - A second hostname for the preview origin.
  - An independent backup destination, a different provider or account (for example

- **Status:** accepted

## ADR-017 Soft delete for artifacts; reference-checked garbage collection for file assets

- **Status:** accepted
- **Decision:**
  - Deleting an artifact sets `deleted_at`. It is hidden everywhere, recoverable, and
    excluded from search and shares.
  - Purge (a later task) hard-deletes versions; the cascade removes `artifact_files` rows.
  - `file_assets` are deleted only by a GC job when no `artifact_files` row references them
    and a grace period has elapsed. `artifact_files.file_asset_id` is `ON DELETE NO ACTION`,
    so the database refuses to delete a file asset that is still in use.

## ADR-018 Export format versions: bump for every added table, read every older version

- **Status:** accepted (PR 13, tags)
- **Context:** Tags are the first data added after export format v1. An optional `tags.json`
  inside "v1" would let an older app restore a newer archive and silently drop the tags:
  a backup that looks complete but is not.
- **Decision:**
  - Every format change that adds data bumps `formatVersion` (v2 = v1 + `tags.json` and
    `artifact_tags.json`). Exports are written in the latest version.
  - Restore keeps a schema per version and reads every supported one (a v1 archive has no
    tags). An unknown version is refused with `UNSUPPORTED_EXPORT_FORMAT`, which names the
    versions this app reads.
  - Restored tags merge by normalized name; an artifact that already exists keeps its own
    tags (BACKUP_RECOVERY §6).
- **Consequences:** Collections, notes and reading state will each bump the version again
  (or ship together in one bump). The round-trip test restores a rewritten v1 archive, so
  backward compatibility is checked on every change.

## ADR-019 Notes and reading state in backups: notes return, reading state is merged

- **Status:** accepted (PR 16, notes and reading state)
- **Context:** Notes are content the owner wrote; reading state (unread / reading / read,
  favorite, last opened) is per user. Users are never exported (BACKUP_RECOVERY §1), and a
  restore runs as one user.
- **Decision:**
  - Format v4 adds `artifact_notes.json` (without authors: restored notes belong to the
    restoring user) and `artifact_reading_states.json` with **one state per artifact merged
    over the workspace's current members** (a removed member's states are left out): favorite
    if anyone marked it, the furthest status anyone reached, and the latest time anyone
    opened it.
  - Restore gives a newly restored artifact its archived state for the restoring user; an
    artifact that already exists keeps the user's current state.
  - Notes an existing artifact lacks are added back, as versions are (tags and collection
    items are not: they are organization, and a removed tag stays removed). A note deleted
    after the export therefore returns on a restore of that export.
- **Consequences:** A personal vault restores exactly. A shared workspace loses whose state
  was whose (it was never exported). Re-running a restore after deleting a note brings the
  note back; deleting it again is the remedy.

## ADR-020 Share links: hashed tokens, a narrow capability, and visibility that follows links

- **Status:** accepted (PR 17, share links)
- **Context:** FR-SHR asks for links that let someone without an account read one artifact,
  with separate reading / preview / download permissions, expiry and revocation. The vault is
  private by default, and its preview origin serves untrusted HTML behind short path tokens.
- **Decision:**
  - A link's token is 32 random bytes (base64url). Only its SHA-256 is stored, so neither the
    database nor a backup holds a usable link; the URL is shown once. Links are never
    exported.
  - `resolveShare` turns a token into a capability (one artifact's current version, the
    link's permissions) only while the link is not revoked or expired and the artifact is not
    deleted, private or restricted, re-checked on every request. The public routes take only
    that capability; no service ever runs with an anonymous actor. Every failure is one 404.
  - Previews reuse the preview origin with a `share` scope that carries the link id; the
    preview route checks the link on every file, so revocation is immediate.
  - Visibility follows links: creating one makes a private artifact `unlisted`, and making
    it private revokes every link permanently (re-unlisting never revives old URLs).
    `public` stays reserved for the Phase 4 showcase.
  - The pre-share check is advisory (patterns can neither prove a document clean nor catch
    everything); only `restricted` blocks sharing.
  - Anonymous routes are rate limited in Postgres (`rate_limit_buckets`, fixed windows, one
    atomic upsert), keyed by the trusted client address.
- **Consequences:** A lost URL cannot be recovered, only replaced. Revoking is instant for
  pages, files and previews; a download URL already handed out lasts its 5 minutes. A link
  shares whatever version is current, including ones added after it was created. Rate limits
  are only as good as the client address (DEPLOYMENT §5.6). Restores bring artifacts back
  without links. Restriction and deletion suspend links; a future undo of either must revoke
  them.

## ADR-021 Version split: the version moves to an artifact made as its import would have made it

- **Status:** accepted (PR 21, version split)
- **Context:** Imports add a file as a new version of the one artifact whose identity key (the
  normalized filename stem) it shares (IMPORT_PIPELINE §6). Two unrelated documents with
  similar names get merged, and nothing could undo it: versions cannot be deleted, and
  originals are immutable.
- **Decision:**
  - `POST /api/artifacts/:id/versions/:versionId/split` moves one version to a new artifact
    in one transaction. The version keeps its id, files, extractions, derived files and search
    chunks (only `content_chunks.artifact_id` is rewritten); it becomes V1 there.
  - The new artifact is made as the import would have made it alone: title from the
    extraction or the filename, summary from the text, identity key from the filename,
    private, in the old artifact's project. It keeps the old artifact's sensitivity (a
    restricted work's version must not become shareable by being split off). It belongs to no
    collection and has no tags.
  - Everything the owner attached to the old artifact stays there: notes, tags, collections,
    reading state, share links. Its other versions keep their numbers (gaps are fine); if the
    split version was current, its newest remaining one becomes current, and otherwise the
    current version stays. An only version cannot be split (409): that would leave an artifact
    without versions.
  - Versions are locked before their artifact, as the search index job takes them: the moved
    version, and the newest remaining one, which becomes current (pointing the artifact at it
    takes a key-share lock on it, which must not wait while the artifact is held). The two are
    locked in id order, and the remaining one is checked again once the artifact is locked;
    if versions changed in between, the split starts over (at most three times). So a split
    cannot deadlock with indexing, and an index job queued behind it writes its chunks to the
    new artifact.
  - The new artifact's name and identity key come from the name the version was uploaded
    under (`artifact_files.display_name`), not the stored original's, which can be an earlier
    upload's when the same bytes came in before.
  - The import item keeps `result_artifact_id` = the old artifact: it records what the
    import did.
- **Consequences:** Version numbers are positions, not ids: after the newest version is split
  off, the next import takes its number again (the audit log records version ids). Two
  artifacts now share an identity key, so later files with that stem
  match neither and become new artifacts with `AMBIGUOUS_VERSION_MATCH` (the owner can target
  one explicitly). Share links of the old artifact keep showing its current version, which
  may change. Notes written about the split version stay with the old artifact. An archive
  made after a split, restored with `skip_existing` over a database saved before it, cannot
  bring the new artifact back (its version is still in the old one, which is kept as it is);
  the report says so and copy mode restores it as a copy. In that restore, a version added
  under the reused number is skipped too ("already has a different version"). There is no
  merge (the reverse) yet.
